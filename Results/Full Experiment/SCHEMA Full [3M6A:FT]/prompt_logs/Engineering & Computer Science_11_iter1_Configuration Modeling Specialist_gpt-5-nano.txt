Incremental Build Architect: "Summary proposal for pyrobuilds core incremental-build mechanisms.

Core model and invariants
- Represent the build as a directed acyclic graph (DAG) of tasks (actions) whose nodes are pure functions from declared inputs + configuration parameters to outputs. The system enforces two key invariants: (1) action determinism (same inputs+config -> same outputs) and (2) complete dependency declaration (all inputs used must be declared or discovered). These invariants can be strengthened by hermetic execution and sandboxed I/O tracing.

Key data structures
- GraphStore: compact DAG with nodes = {action-id, declared-params, outputs, fingerprint}. Edges = declared deps and dynamically discovered deps.
- ArtifactStore (content-addressable store, CAS): stores blobs by content hash and maps outputs to CAS keys.
- CacheIndex: mapping from action-signature-hash (action code + declared inputs' CAS + config) -> output CAS keys.
- ChangeIndex: maps filesystem paths / configuration keys -> last-seen content hash for fast change detection.
- Dependency-trace logs: per-action recorded file-access traces for dynamic-deps and validation.

Action and fingerprinting
- Action signature = hash(action code + tool versions + environment fingerprint + configuration parameters).
- Action input fingerprint = ordered multiset of input CAS keys + declared implicit inputs.
- Node fingerprint = hash(action signature || input fingerprints). This is the cache key used to determine reuse.

Incremental algorithm (high level)
1. Change detection: compute diffs of input files and configuration using ChangeIndex and CAS (fast negative checks via bloom filters).
2. Dirty set computation: mark nodes whose input fingerprints changed; propagate changes to reverse-deps using BFS/DFS on GraphStore to compute minimal affected subgraph.
3. Reuse decision: for each affected node in topological order, check CacheIndex for matching node fingerprint. If present, reuse CAS artifacts; if not, schedule execution.
4. Execution: run actions in sandboxed environment that enforces declared inputs/outputs and records actual filesystem accesses. Use two-phase execution for dynamic deps: probe/scan phase that discovers deps, update DAG, then full execution if necessary.
5. Commit: store outputs in CAS, update GraphStore and CacheIndex atomically.

Dynamic dependencies and correctness
- Two approaches: (A) conservative mode: assume possible dynamic deps (e.g., full directory); (B) discover mode: run actions in a tracing sandbox and then update DAG; always treat missing/undiscovered accesses conservatively to avoid under-builds.
- Hermetic mode uses containerized executions and explicit tool-version fingerprints for strict reproducibility; permissive mode trades strictness for speed.

Optimizations for large configuration spaces
- Parameterized caching: include configuration parameters in action signature so identical actions across variants reuse outputs when inputs match.
- Shared subgraph canonicalization: canonicalize equivalent intermediate artifacts across configurations to maximize cross-config reuse.
- Lazy materialization: keep many artifacts in CAS remote cache and only materialize to disk on demand.
- Partitioned scheduling + parallel execution with concurrency limits and remote-exec support to scale.

APIs and integration
- Declarative API: actions declare inputs, outputs, implicit inputs, config parameters, environment constraints.
- Tracing wrapper: lightweight toolchain adapters that run commands under sandbox/tracer to capture file-level deps and tool versions.
- Remote cache API: push/pull CAS artifacts and index entries for cross-machine sharing.

Prototype components to implement first
- CAS-backed ArtifactStore, GraphStore, ChangeDetector, and a sandboxed ActionExecutor with file-access tracing.
- Minimal CacheIndex and scheduler to demonstrate correctness and cross-config reuse.

This design prioritizes minimal rebuilds via content-addressable caching and strict fingerprinting, preserves correctness by conservative dependency handling and sandboxed tracing, and scales across large configuration spaces via parameterized caching and shared subgraph reuse."
