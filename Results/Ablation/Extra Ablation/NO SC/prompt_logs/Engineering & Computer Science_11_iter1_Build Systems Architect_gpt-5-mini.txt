Core formal model:
- Nodes: tasks t ∈ T with deterministic actions A_t that map inputs and configuration c to outputs.

- Dependency graph: a directed acyclic graph where edges include configuration semantics (edge labels include input selection functions parameterized by c).

Data structures:
- Content-addressable storage (CAS) for artifacts indexed by build key and artifact hash.
- Merkle DAG for provenance: each artifact node stores pointers to dependency artifact hashes and configuration metadata.

- Config similarity index: clusters configurations by input-selection overlap to prioritize reuse across similar variants.

- Use fingerprint-based bottom-up propagation: when a primitive input or config parameter changes, recompute fingerprints for affected leaf nodes, then propagate upwards. A node is dirty iff any dependency fingerprint or its config component changed.

Key incremental-update ideas and their trade-offs
- Patch-based artifact reuse across configurations
  - Idea: for a given task t, store a library of configuration-variant patches P(c1→c2) that capture how A_t’s output changes when the configuration changes while inputs remain fixed. When moving from c1 to c2 and all dependencies’ fingerprints match, apply the patch to the cached artifact K(t,c1) to obtain K(t,c2) without full recomputation.
  - Benefits: reduces recomputation when configuration changes are small; amortized cost O(|patch|) versus O(T_t).
  - Requirements: deterministic A_t; patch composability across successive config changes; patch provenance tracked in the Merkle provenance DAG.

- Partial-artifact reuse with input partitioning
  - Idea: decompose artifacts into subcomponents aligned with input domains (e.g., specific files, env vars, or dependency groups). If only a subset of inputs or a subset of config choices changes, reuse the corresponding sub-artifact(s) and re-run only the affected subgraph.
  - Benefits: finer-grained reuse; can yield large savings when changes are localized.
  - Trade-offs: added bookkeeping and patch composition complexity; risk of flaky provenance if subcomponents interact subtly.

- Config-similarity-aware caching
  - Idea: cluster configurations by input-selection overlap and configure a cache hierarchy where a single cached artifact from a nearby configuration can seed nearby configurations with patches or partial recomputations.
  - Benefits: higher reuse probability across exploration batches; reduces cold-start costs.
  - Requirements: robust similarity metrics, threshold tuning, and careful soundness guarantees when propagating partial results.

- Eager-vs-lazy hybrid scheduling with budgeted precompute
  - Idea: allocate a small budget to precompute plausible high-reuse variants (guided by similarity, historical hit rates). Fall back to lazy on-demand recompute for less promising variants.
  - Benefits: improves average hit rate without blowing up memory; tunable via budget and prediction model.
  - Trade-offs: potential cache pollution if predictions are off; need eviction policies that respect provenance.
