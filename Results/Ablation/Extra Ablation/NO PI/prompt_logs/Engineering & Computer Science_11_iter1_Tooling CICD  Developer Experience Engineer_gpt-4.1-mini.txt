Incremental Build Systems Architect: "High-level design summary: pyrobuilds will represent every build as a content-addressed Merkle DAG of actions and artifacts, where each action is hermetic, declares its inputs and parameters, and produces content-addressed outputs stored in a pluggable CAS. Cache keys are precise action signatures (action key = hash(action proto, toolchain digest, declared inputs' digests, normalized parameter hash, action-version)) so identical work across configuration sweeps is deduplicated automatically. The system separates configuration-invariant graph fragments from parameterized nodes so shared intermediates are reused across many variants.

Core model and data structures: nodes are Actions {id, command-spec, declared-inputs:set<digest>, params:map, toolchain-id, version}, and Artifacts {digest, size, storage-loc, provenance}. The global build graph is a typed DAG of Action -> Artifact -> Action edges; nodes map to CAS digests for fast equality. Build state is a Merkle snapshot so partial reuse is a pure function of inputs + action key.

Caching strategies:
- Content-addressed CAS as source of truth for artifacts and toolchains, with pluggable backends (local disk, S3, GCS, remote cache).
- Two-level caching for config sweeps: shared global cache for configuration-invariant artifacts, and variant-indexed mapping for outputs that intentionally depend on parameters. Action keys include a normalized param hash so identical flags reuse outputs.
- Fine-grained input tracking: declare file-level inputs and use content digests; for opaque tools, provide a sandboxed tracing fallback to capture undeclared inputs and enforce failure or record warnings.
- Partial reuse via parameter factoring: allow rule authors to split actions into pre-processing (config-invariant), parameterized transformation, and packaging phases so the preprocessed artifact is reused across many configs.
- Speculative/prewarming: provide ability to warm remote cache with likely artifacts for a configuration sweep.

Correctness and invalidation:
- Hermetic actions run in sandboxed environments (namespaces / containers) with only declared inputs to ensure cache key correctness.
- Action-versioning and toolchain digesting provide forward-safe invalidation when behavior changes.
- Provenance metadata stored per artifact: action key, timestamp, builder id, log; rebuild is forced if provenance mismatch or sandboxed trace finds undeclared inputs.

APIs and integration points:
- Declarative rule API: declare_action(name, inputs, params, outputs_hint, toolchain).
- Cache API: query_cache(action_key) -> artifact_digest | miss; store_cache(action_key, artifact_digest, provenance).
- Graph API: add_node, connect_nodes, plan_build(roots, params), dry_run/graph_query.
- Execution API: schedule(action_key, sandbox_spec, concurrency), remote_execute/return_logs.

Extensibility and engineering notes:
