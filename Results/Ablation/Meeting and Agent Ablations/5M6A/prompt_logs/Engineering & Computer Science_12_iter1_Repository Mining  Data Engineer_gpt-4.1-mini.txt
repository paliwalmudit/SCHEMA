- Distinguish levels: file-level (a .go file uses import "C"), package-level (any file in package uses cgo), repo-level (any package uses cgo), and runtime/link-time dependency (linking requires native libraries even if top-level package has no import "C").

Taxonomy of cgo usage patterns (for labels)
1. Direct FFI: import "C" + explicit C code or calls to C functions in the preamble. (most clear-cut)
2. Link-only: package supplies only // #cgo LDFLAGS or pragma-based linking to system libs without calling C functions (sometimes used to make symbols available at link time).
3. Header/flag-only: Uses CFLAGS, pkg-config or includes headers in preamble but no runtime C calls (may be preparatory or unused).
4. Generated-binding (SWIG, c-for-go, SWIG wrappers): generated Go wrappers that call C (often identifiable by generator comments or .swig files).
5. Test-only cgo: cgo usage confined to *_test.go files.
6. Transitive cgo: package itself has no import "C" but depends on packages that do; building final artifact may still require cgo or native libs.
7. Build-tool/CI cgo usage: CGO_ENABLED toggles or native-toolchain installation in CI/Dockerfiles; repo doesn’t contain import "C" but CI config shows cgo dependence.
8. Low-level linker directives: use of compiler directives like //go:cgo_import_dynamic or assembly directives that embed dynamic linking behavior.

Detection signals and heuristics
- Strong positive signals: import "C" in parsed AST; // #cgo directives in comments; presence of .c/.h/.hxx/.cpp files adjacent to packages; .swig/.i files; explicit -l/-L/-I flags in preamble; pkg-config usage in comments.
