Annotation rules (port-level semantics)
- Define a link as a conductive connection: two ports are linked iff they belong to the same conductive net in the canonicalized netlist or are explicitly connected by an ideal declared connection (wire, instance pin mapping). Do not label capacitive/inductive coupling as a conductive link; treat those as separate edge types if modeled.
- Hierarchy: flatten instance pins for connectivity but preserve instance identity in metadata. If hierarchical instances create ambiguous nets (aliases), propagate canonical net IDs and mark alias mappings in label_reason.
- Device internals: treat multi-pin devices (BJTs, MOSFETs, op-amps) ports individually; explicitly record body/bulk ties as ports and label their links separately. For dependent sources and behavioral devices, follow declared nets; if nets are implicit, require human review.
- Power rails and global nodes: normalize power net aliases (VDD/VCC/VSS/GND) and apply consistent rules; mark regulated rails as normal nets, but allow a special tag for common power rails for targeted evaluation.
- Floating ports: label as no-link. If a net is single-ended and intentionally floating, annotate label_reason=floating.
- Parameter normalization: coerce units (S, F, ohm, µm) and annotate nominal bias points when present.

Validation and SPICE checks
- Automated graph equivalence: validate that canonical netlist graph is isomorphic in conductive connectivity to a parser-derived graph; fail conversion if mismatch.
- Electrical spot-checks (apply to a validation subset): run SPICE DC operating point and compare node voltages for key nodes (tolerance e.g., 1–5% or absolute depending on scale). Run small-signal AC or transient tests for representative circuits and compare gain/phase or transient waveforms (normalized RMSE thresholds).
- Consistency checks: ensure every declared port belongs to exactly one component and each net has >=1 member (or explicit floating flag). Verify port counts match device models.

Realistic failure modes to monitor
- Net aliasing/hierarchy flattening errors that merge distinct nets or split single nets.
- Unit/parameter conversion errors causing unrealistic device bias points.
- LLM hallucinations producing nonexistent components or incorrect pin orders.
- Implicit nodes (e.g., default reference nodes) lost during canonicalization.
- Missing body/bulk ties for transistors leading to incorrect connectivity.

Augmentation and weighting strategies
- Weight training examples by Netlist Babel Fish conversion_confidence; set human-review threshold (suggest <0.8).
- Augment with topology-preserving perturbations: parameter jitter, duplicate motif insertion, and format-noise variants (token reorderings) to increase robustness.
- Pretrain on synthetic graphs with guaranteed ground truth, then fine-tune on high-confidence real data.

Benchmarks and evaluation
- Port-level metrics: precision, recall, F1, AP, precision@k, and recall@k.
- Circuit-level metrics: functional recovery rate (proportion of circuits where key QOIs match within tolerance), graph equivalence rate, and SPICE-based electrical equivalence (DC node errors, AC transfer RMSE).
- Robustness tests: leave-one-type-out, format-noise OOD, and confidence-threshold curves.
