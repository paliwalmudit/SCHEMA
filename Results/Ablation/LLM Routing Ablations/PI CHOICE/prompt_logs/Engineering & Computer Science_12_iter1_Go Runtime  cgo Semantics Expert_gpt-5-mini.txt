Exploitability: High when pointers reach long-lived C state. Detection: SSA points-to + escape analysis, detect flows from Go pointer -> _Cfunc_* -> C global or allocated structure. Heuristic: flag when pointer origin is stack-local or when stored in C global/static.
2. uintptr/unsafe conversions — pointer -> uintptr -> C and back. Severity: High. Exploitability: Moderate–High. Detection: track unsafe.Pointer/uintptr casts in SSA and conservatively escalate.
3. Stack vs heap ambiguity — passing addresses of stack-allocated locals or slices into C. Severity: High. Detection: determine allocation site via escape analysis; flag stack-allocated addresses or &slice[0] where slice can reallocate.
4. Callbacks from C threads (unregistered threads) — C-created threads calling exported Go functions or Go runtime APIs. Severity: High. Exploitability: High (runtime invariants broken). Detection: parse C AST for pthread_create/CreateThread + callback reaching //export symbols; flag long-lived threads.
5. //export misuse and runtime invariants — high-frequency exported functions or exported functions that assume Go runtime state. Severity: Medium–High. Detection: count call frequency, check for exported handlers used by C threads.
6. Ownership/memory-management mismatches — C freeing Go memory or double-free patterns. Severity: Medium. Detection: heuristics linking malloc/free usage with pointer provenance.
7. Data races and concurrency hazards — unsynchronized access across Go and C contexts. Severity: Medium. Detection: identify shared mutable state passed to C and concurrent C callbacks.
8. ABI/portability and build-time hazards — mismatched struct packing, platform-specific macros, custom CC flags. Severity: Medium. Detection: inspect // #cgo flags, preprocessed headers, and type-size mismatches.
9. Vulnerable native dependencies — use of C libs with known CVEs. Severity: Variable. Detection: symbol/library fingerprinting (nm/objdump) and CVE matching.

Triage scoring and reporting
- Score each finding by Severity (impact), Exploitability (ease), Reproducibility (build artifacts present), and Confidence (static evidence). Prioritize High impact × High exploitability × High confidence.
- Present provenance: repo, commit, package, file/line, build flags, generated wrapper names, and minimal reproduction snippet.

Mitigations and recommended fixes
- Prefer copying data into C-allocated memory or use cgo.Handle for opaque Go values when storing in C. Avoid passing Go stack addresses; ensure values escape to heap if required.
- Avoid uintptr shims; where unavoidable, document and isolate with static assertions and tests.
- For callbacks, require C threads to call runtime.LockOSThread and use documented registration patterns; prefer Go-created threads when calling into Go.
- Add explicit ownership conventions in bindings and free wrappers in C.
- Add runtime debug mode (CGO_DEBUG) that checks long-lived C storage of Go pointers and rejects unregistered thread callbacks.

Recommendations for Go team and cgoanalyzer integration
- Expose richer metadata in generated cgo artifacts (explicit mapping files, lifetime annotations) to reduce false positives.
- Provide a vet/lint rule set derived from the above detectors and an optional runtime assertion mode.

Map the unnormalized evidence vector to a normalized score in [0,1] and tie disclosure actions to thresholds. Example unnormalized weights: direct SSA flow=4, cgo-artifact presence=3, C-store/malloc evidence=3, build reproducibility=1, uintptr-only penalty=−1. Normalize and publish calibration curves (ROC/PR and reliability plots) computed on the labeled validation set. Suggested operational thresholds: >0.75 = High (candidate for private disclosure), 0.40–0.75 = Medium (informational, maintainers suggested fixes), <0.40 = Low (audit-only). Provide sensitivity sweeps (±25% on each weight) and publish impact on prevalence to allow stakeholder policy choices.

2) Recall-improving seeded corpus and mutation operators
Seed a synthetic corpus with canonical fixtures: stack-vs-heap pointer passing, uintptr round-trip shims, C-created-thread→Go callbacks, //export misuse, C global storage of Go pointers, C++ extern "C" wrappers, varargs/struct packing edge cases. Mutation operators: 1) insert/remove intermediate C globals or malloc wrappers; 2) rewrite direct pointer flows to uintptr/unsafe casts; 3) add wrapper name mangling (C++/Itanium/MSVC); 4) wrap Go pointer storage via inline assembly or opaque C handles; 5) inject pthread_create/CreateThread call sites. Use these to bootstrap recall estimates and compute bootstrap CIs.

3) Minimal dynamic corroboration harness
Provide lightweight dynamic checks that materially increase confidence: (a) CGO_DEBUG logging to record pointer provenance and cross-language calls, (b) sanitizer-enabled builds (ASAN/UBSAN) where native UB might surface, (c) small fuzz-litmus runner that exercises flagged wrappers and C-thread callbacks under hermetic builds and reports failures. When dynamic evidence reproduces a hazardous behavior, add a calibrated confidence boost (e.g., +0.15) and mark finding as dynamically corroborated with artifact provenance.

4) C++/Obj‑C/Windows heuristics
Detect extern "C" wrappers by parsing generated _cgo_export.h and preprocessed headers; demangle common ABIs (Itanium/GNU, MSVC) when referenced by wrappers and conservatively taint mangled names. Treat template-only/mangled-only symbols as tainted sinks when referenced by _Cfunc_* wrappers. Flag objc_msgSend/@selector usages as potential callback sinks. For Windows, include MSVC and clang-cl toolchains in CI; parse // #cgo directives for calling-convention hints and conservatively assume the most permissive calling convention when uncertain (treat as potential mismatch).

5) Timeouts, budgets, and reporting
Default per-package timeout 3 minutes and per-repo budget 30 minutes with an 8 GB memory cap; allow overrides for heavy builds. If analysis times out, emit annotated partial findings with a "partial=true" flag and list which detectors timed out so downstream reviewers know limits.

6) Publishing schema and redaction
Use JSONL/Parquet schema with fields: repo_url, commit_sha, package, file, line, detector, normalized_confidence, confidence_components, artifacts_present, dynamic_evidence (bool + details), reproducible_build (bool), redacted (bool), notes. Redact PII (author emails, API tokens, private paths) and exclude non-redistributable repos. Publish calibration artifacts, labeled validation sets (redacted), and vet-rule proposals (go vet + golangci-lint) along with remediation snippets to maximize maintainer uptake.

These steps map static findings to concrete runtime semantics, reduce false negatives, and make triage/disclosure decisions reproducible and defensible.
