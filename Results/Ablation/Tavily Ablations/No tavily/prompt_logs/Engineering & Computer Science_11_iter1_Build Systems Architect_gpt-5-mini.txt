As Build Systems Architect for pyrobuilds, my core objective is to guarantee correctness while minimizing unnecessary rebuilds across large configuration sweeps. Below is a focused design summary and implementation plan for the incremental-build engine that balances soundness and performance.

Build graph model and provenance
- Model the build as a directed acyclic graph of actions (nodes) where each node records: declared inputs and outputs, the action command, environment and toolchain identifiers, and explicit configuration parameters that influence it.  
- Represent content provenance using a Merkle DAG: each node’s cache key is a cryptographic digest derived from the node’s command signature and the digests of its inputs (files, upstream node outputs, and parameter values). This makes cache keys deterministic and comparable across builds.

Change-detection and cache keys
- Compute cache keys from: (1) content hashes of declared input files, (2) action command hash, (3) environment/toolchain identifiers (versions), and (4) a curated tuple of configuration parameters that actually affect the action.  
- Treat filesystem metadata (mtime) as a fast conservative heuristic: if mtime changed, schedule content rehash; otherwise skip hashing unless in aggressive correctness mode. Use parallelized content hashing and sampling for large inputs to reduce cost.

Dynamic dependencies and discovery
- Support dynamic dependency discovery by running a short sandboxed "discovery" phase for actions that declare dynamic inputs. Capture actual read/write traces via lightweight syscall tracing or sandboxed filesystem interception to record extra dependencies, then recompute cache keys with those discovered inputs before executing the main action. This ensures soundness for actions that depend on runtime input lists.

Configuration-sweep optimization
- Parameter-sensitivity (slicing): annotate which parameters affect which nodes. During configuration sweeps, only invalidate nodes whose parameter set intersects changed parameters. Store outputs keyed by both node digest and parameter projection to enable reuse across many configurations.  
- Compute shared subgraph once: factor the graph into common and variant subgraphs; execute and cache the common portion once and reuse across all configurations.

Cache invalidation and GC
- Strict rule: a node is rebuildable (skippable) if and only if the current cache key equals the stored key and all declared inputs’ digests match. This guarantees correctness.  
- Provide configurable pragmatic modes (conservative vs. aggressive). Conservative mode rehashes more often; aggressive mode trusts mtimes and recorded digests for speed. Implement content-addressable storage (local CAS + optional remote cache) and safe garbage collection based on usage metadata and TTLs.

Integration and observability
- Expose APIs for declaring parameter sensitivity, dynamic deps, and toolchain IDs. Persist the build graph, recorded digests, and action metadata between runs. Instrument with cache-hit/miss metrics, dependency traces, and per-node rebuild rationale for debugging.

Next steps and experiments
- Prototype: implement Merkle-based cache keys, mtime+lazy hashing, and parameter-sensitivity tagging.  
- Empirical evaluation: measure cache hit-rate and hashing overhead on representative large sweeps, compare discovery approaches (syscall tracing vs. sandbox replay), and tune the mtime vs hashing threshold.

This design guarantees correctness by making rebuild decisions solely on verifiable provenance while minimizing unnecessary work through parameter-aware caching, discovery, and shared-subgraph reuse.
